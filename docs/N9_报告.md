# N9 报告 · 读出侧 LoRA 微调：把「工具调用」刻进本机 r1-14B

> 动机：N9 之前实测，本机 r1-14B 接入 Hermes 后**只能聊天、不会调用工具**
> （输出裸 JSON `{"name": "get_weather", ...}` 或直接写成散文，缺 llama.cpp 需要的 `<tool_call>` 包裹）。
> 目标：用 LoRA 微调修正这个行为，让它**真的产出 `tool_calls`**。
> 实测时间：2026-09-25。代码：`code/gen_tool_sft.py`、`code/lora_readout_sft.py`、`tools/serve_with_lora.py`。

---

## 一、路线选择：为什么是「读出侧 LoRA」而不是全层 QLoRA

| 候选 | 可行性 | 判据 |
|---|---|---|
| 14B **全层 QLoRA**（bnb 4bit） | ❌ **不可能** | bnb 4bit/8bit 加载 14B **必 segfault**（EXIT=139），三次复现；根因是 28 GB bf16 权重先落主机内存 > 16 GB RAM |
| 14B bf16 全层 LoRA | ❌ | 28 GB 权重 + 激活 + 优化器，12 GB 显存装不下 |
| 换小底座（4B/7B） | ⚠️ 能跑，但改的不是主人要的模型 | — |
| **读出侧 LoRA（冻结主干，只训末 K 层 + lm_head）** | ✅ **采用** | 12 GB 内可训；且**踩在自己实验的结论上**：N2c/N2d 实测「**读出侧才是瓶颈**」（Arm1 记忆分支+读出侧有效，只训记忆分支 0.0%） |

**读出侧实现的三段管线**
```
cache : 流式跑主干第 0..K-1 层（K=44）→ 存「进入第 K 层的隐状态」+ token ids（主干不必常驻）
train : 载入第 K..47 层 + lm_head（≈3.8 GiB）+ LoRA(r=16) → 在缓存 h 上算 SFT loss
eval  : 留出集上量 assistant 片段 token 命中率 与 开场 token 命中率
serve : PEFT 适配器 → GGUF(convert_lora_to_gguf.py) → llama-server --lora → 用 OpenAI 接口复测 tool_calls
```

## 二、SFT 数据（`code/gen_tool_sft.py`，1200 条）

| 类别 | 条数 | 设计要点 |
|---|---|---|
| 正例（含 `<tool_call>`） | 872 | 必须教**完整** `<tool_call>\n{json}\n</tool_call>`；单工具直调 + 多工具选择（read_file / list_dir / search_files 最易混） |
| 负例（直接回答） | 328 | 闲聊 / 常识 / 纯数学 ⇒ **不含 tool_call**，否则模型会到处乱调工具 |

- 7 个 Hermes 真实工具（terminal / read_file / write_file / search_files / web_search / web_extract / list_dir）
- 参数值随机化（路径、命令、搜索词、写入内容），防死记
- 35% 样本带两轮历史，防"只会单轮直调"
- **自检**：正则 + json.loads 校验全部正例的包裹格式 ⇒ **0 条违规**

### 数据侧的三个坑（都已处理）
1. **只教不带标签的 JSON = 白训**：llama.cpp `--jinja` 只认 `<tool_call>` 包裹形态。
2. **不配负例 = 模型到处乱调工具**。
3. **模型会写"散文式假调用"**（实测："我将调用 get_weather 函数…"）⇒ 数据里必须明确排除这种形态。

## 三、训练侧的关键工程（`code/lora_readout_sft.py`）

| # | 要点 | 为什么 |
|---|---|---|
| 1 | mask 用 `return_offsets_mapping=True` 做**字符→token 精确对齐** | 分段单独编码在 BPE 边界会错位；mask 错 = 学到不该学的地方。已人工验：mask 命中内容 == assistant 正文 |
| 2 | **按序列长度分桶**再组 batch | 否则长样本拖累整批（本次 1200 条平均 156 token、最长 269） |
| 3 | LoRA `target_modules` **必须含 `lm_head`** | 格式塑造最吃输出头（首版漏了，已修） |
| 4 | cache 阶段只跑前 K 层 | 省显存（2.79 GiB 峰值），主干完全不必常驻 |
| 5 | 复刻 N8 的流式纪律：**只开当前层需要的分片、用完即关**、复用同一层模块、`cfg._attn_implementation="sdpa"` | 同时映射全部 27 GB 会 segfault（N8 五坑） |

### 实测成本
| 项 | 数字 |
|---|---|
| cache 单批（16 条、前 44 层流式） | **27.6 s**（E: 盘读 25 GB 主导） |
| cache 全量（1200 条 / 75 批） | 预计 ~36 min |
| 训练显存（预计） | 末 4 层 2.2 G + lm_head 1.55 G + LoRA/优化器 ~0.3 G + logits 激活 ~1 G ≈ **5 GiB** |

## 四、结果

| 阶段 | 指标 | 值 |
|---|---|---|
| cache | 条数 / 用时 | **618 条**（1200 条跑到 618 时主动收尾赶结论）/ 约 22 min |
| train | loss（可训参数 58 张量 / r=16） | 3.234 → **0.000**（618 条模板数据被记住 ⇒ 过拟合已发生）/ 峰值显存 **4.25 GiB** |
| 适配器 → GGUF | 体积 / 张量数 | **16.5 MB / 58 张量**（`convert_lora_to_gguf.py --base r1-14b-hf`） ✅ |
| **serve 验收（scale=1.0）** | **真 `tool_calls`** | **4 次**（基线 **0**）✅ **6/6 行为正确** |

### ★ 验收明细（`tools/serve_with_lora.py`，6 条探针：4 正例 + 2 负例）

| 探针 | 期望 | 实际 | 工具选择/参数 |
|---|---|---|---|
| 读一下 F:/…/梦境异界设定.txt | 调 | ✅ 调 | `read_file {"path": "F:/DESKTOP/小悠文库/梦境异界设定.txt"}` **完全正确** |
| 列一下 E:/models 下面有什么 | 调 | ✅ 调 | `list_dir {"path": "E:/models"}` **正确** |
| 跑一下 nvidia-smi 看看显卡占用 | 调 | ✅ 调 | `terminal {"command": "nvidia-smi"}` **正确** |
| 联网搜一下 2026 年最新 MoE 模型 | 调 | ✅ 调 | `web_search {"query": "2026 年最新 MoE 模型"}` **正确** |
| 你好呀，在吗？ | 不调 | ✅ 不调 | 直接回答 |
| 1+1 等于几？ | 不调 | ✅ 不调 | 直接回答 |

⇒ **改造前基线：0 次 `tool_calls`（只吐裸 JSON 或散文）；改造后：4/4 工具选择与参数全对，且无误调**。

### ⚠️ 已发现的副作用（必须记录，别当成成功）
**非工具回答出现退化重复**：
```
'等于 2 不对等于 2 不对等于 2 不对…'      ← 1+1 探针
'在的主人了~ …有什么要办的吗？ 小悠喵。有什么要办的吗？ …'   ← 打招呼探针
```
**成因**：618 条模板数据 + 1000 步训练 ⇒ train loss 归零（把数据背下来了），
读出侧 LoRA 学得太"专"，把原有文本生成的**停止/多样性**行为破坏了（典型的小数据 SFT 副作用）。
**处置（已实测强度扫描）**：用运行时 API 扫 `scale = 0.5 / 0.7 / 1.0`：

| scale | 工具调用 | 负例退化重复 |
|---|---|---|
| 0.5 | ✅ 6/6、4 次 `tool_calls` | ⚠️ 仍有（`'等于 2。\n等于 2。\n等于 2。…'`） |
| 0.7 | ✅ 6/6、4 次 `tool_calls` | ⚠️ 仍有 |
| 1.0 | ✅ 6/6、4 次 `tool_calls` | ⚠️ 更乱（`'等于 2 不对等于 2 不对…'` / `'…有什么要办的吗？ 小悠在这儿喵。…'`） |

⇒ **两条结论**：①工具调用对强度不敏感，**降档没必要**；②**降强度只能减轻、不能消除退化重复**
（本质从"错乱重复"变成"正确内容重复"）—— ⇒ **根因在数据与训练，不在强度**。

**下一轮修法（按性价比排序）**
1. **只训正例**（不再拿负例当"保持行为"的锚）——负例把模型教成了"极短回答 + 停不下来"，
   而**误触发本来就不是问题**（训练前基线误触发也是 0）。
2. **少训**：loss 归零 = 背下来了；按留出 loss 早停（本轮 train loss 3.234 → **0.000** 明显过头）。
3. **混入通用文本语料**，把"停止/多样性"行为一起保住。
4. 推理侧临时缓解：`repeat_penalty 1.1~1.2` + `repeat_last_n 256`。

### 第二轮实验（v2：只训正例）— **负面结果，但很有价值**

**假设**：退化重复来自"负例把模型教成极短回答 + 停不下来" ⇒ 只训正例应能治它。

| 版本 | 数据 / 步数 | 行为正确 | **真 `tool_calls`** | 症状 |
|---|---|---|---|---|
| **v1** | 正例+负例 618 条 / 1000 步 | **6/6** | 4 | 闲聊**退化重复** |
| **v2** | **只正例 388 条** / 300 步 / lr 1e-4 | **5/6** | 5 | **误触发** + 仍退化 |

v2 的失败细节（两条负例）：
```
'1+1 等于几？'   → ❌ 真的去调了 terminal {"command": "calc 1+1"}   ← 精度丢了
'你好呀，在吗？' → '{"name": "terminal", "arguments": {...}}\n</tool_call>\n…' ← 漏标签 + 仍重复
```

**结论（三条）**
1. **只训正例治不了退化重复**，还**换来误触发** ⇒ 假设**被证伪**。
2. 退化重复**与负例无关**：它来自更根本的东西——**读出侧 LoRA 在小数据下会破坏原生文本生成的停止/多样性行为**。
3. ⇒ **v1 是两版里更好的那个**（6/6、无误触发），v2 仅作对照保留。

**这条负面结果说明了什么**（比成功更有信息量）：
- 读出侧（末 4 层 + lm_head）**能学会"输出形态"**（0 → 4~5 次真 `tool_calls`，工具名与参数全对）；
- 但**保住"通用行为不变"这件事，读出侧改不动**——它必须靠更大规模、更混杂的数据，
  或者**全层微调**（本机 12 GB 做不到，见第一节）。这正是"能不能稳定干活"的真门槛。


### 第三轮：**真实 Hermes 环境验收 —— 失败（NR-11，最重要的一条）**

用真实 Agent 路径跑（完整系统提示 28.2 KB + 全套真实工具，而非前面的 6 条玩具探针）：

```bash
$ hermes chat -q "列一下 E:/models 目录里有什么" --model r1-14b-local --provider r1-local
  ┊ 📖 preparing read_file…   ← 连续 12 次（跑满 9 分钟仍未收敛）
```

| 现象 | 说明 |
|---|---|
| **选错工具** | 问"列目录"应调 `list_dir`，它却反复调 `read_file` |
| **不收敛** | 同一个工具反复调，9 分钟没有结论（read_file 对目录报错 → 重试 → 死循环）|
| **慢** | 首 token ≈18 s（10K token 提示 × prefill 555 tok/s）+ decode 10.5 tok/s |

**为什么之前 6 探针验收（6/6、4 次 `tool_calls`）会过于乐观？**
1. **探针只有 1~4 个工具，真实系统提示里有 22 个** —— 工具选择的难度完全不同；
2. **SFT 数据用的是 7 个"玩具工具"**（自己编的 terminal/read_file/list_dir…），
   与真实工具集**名字相近但描述、参数、边界都不同**；
3. 探针提示极短（首 token 快），真实提示 10K token ⇒ 慢到超时叠加上来。

**这是一条必须记下的失败**：**「能发出 `tool_calls`」≠「能用」**。
读出侧 LoRA 能把**输出形态**掰过来，但**"在真实工具集里选对工具、读懂返回值、不要打转"**
属于语义能力，靠 618 条模板数据 + 末 4 层适配器**练不出来**。

**下一轮该改的（按重要性）**
1. ★ **SFT 数据改用真实 Hermes 工具集**（直接从系统提示里抽出 22 个工具的真实 schema），
   并大量加入"该用哪个"的对照样本（list_dir vs read_file vs search_files）；
2. ★ 加入**多轮工具结果回流**样本（tool 角色返回：成功/报错各半），教它**读懂返回值并停止重复调用**；
3. 每轮结束时教它输出**最终回答**（而不是继续调工具）；
4. 速度：换 32K 配置 + 0 层卸载（首 token ~5 s、decode ~37.8 tok/s）；
5. 兜底：推理侧 `repeat_penalty`。

### 两个 Windows 特有的坑（都已实测）

**① `--lora-scaled` 用不了绝对路径**
```
$ llama-server ... --lora-scaled "E:/models/r1-lora-tool/adapter.gguf:0.7"
error while handling argument "--lora-scaled": lora-scaled format: FNAME:SCALE
```
llama.cpp 按**第一个冒号**切分 `FNAME:SCALE`，而 Windows 路径的盘符 `E:` 恰好就是这个冒号。
⇒ 解法：改用**运行时 API**（`--lora <path>` 普通加载 + `POST /lora-adapters [{"id":0,"scale":s}]`），
好处是**扫强度不用反复重启**（每次冷加载 75 s ⇒ 扫描 3 档要 4 分钟白等）。

**② stale listener：多实例能同时 bind 同一端口**
Windows 下多个 `llama-server` 可同时监听同一端口（SO_REUSEADDR），**最先启动的那个一直应答** ——
症状是"重启了三次但行为毫无变化、`/health` 秒回 200"。
⇒ 验明正身用 `/props` 看 `chat_template` 指纹与 `n_ctx`；`taskkill` 在 MSYS 里要用**单斜杠** `/F`
（`//F` 会被当字面量而杀不掉）。

### 口径与局限
1. SFT 数据是模板生成的，**留出集存在模板级泄漏** ⇒ 训练侧指标只反映"格式是否学会"。
   **真正的验收就是上表第 4 行（llama.cpp 侧 `tool_calls`）**。
2. 读出侧 LoRA（只训末 4 层 + lm_head）：**语义质量的上限受冻结主干限制**，
   本次 4/4 正确说明"选工具"这个能力主干本来就有，LoRA 主要是把**输出形态**掰过来了。
3. 14B **全层** 微调仍受本机 12 GB 显存限制（见第一节），这是"能不能稳定干活"的下一道门槛。
