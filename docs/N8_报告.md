# N8 报告 · 给本机 r1-14B 自训 MTP 头（速度轴第二把刀）

> 目标（计划书 §12A.2 S1）：本基底**没有 MTP 头**，而投机解码是唯一"一次读权重、多产出 token"的免费加速。
> 自训 1 层 MTP 头（≈0.28 B，共享 embed/lm_head），判据 **α₁ ≥ 0.6**。
> 实测时间：2026-09-25。代码：`code/mtp_n8s1.py`（新）、`code/mtp_head_train.py`（旧版，整模型加载，本机不可用）。

---

## 一、先说结论：**"整模型加载"这条路在本机是死的，但换成"逐层流式"后全线打通**

| 尝试 | 结果 |
|---|---|
| `AutoModelForCausalLM.from_pretrained`（bf16，28 GB） | 显存 12 GB / 内存 16 GB 都装不下 ❌ |
| bitsandbytes **4bit**（`device_map={'':0}` / `auto` + max_memory） | **EXIT=139 segfault**（`Loading weights: 0%`）❌ |
| bitsandbytes **8bit** | 同上 **EXIT=139** ❌ |
| 对照：同一环境下 **1.5B** 的 4bit 量化 | ✅ 正常（显存 1.13 GiB） |
| **逐层流式加载**（本报告的新工具） | ✅ **48 层 30.3 s，峰值显存 1.98 GiB** |

**根因判断**：bnb 量化要把 bf16 权重先落主机内存（28 GB > 16 GB），**爆内存在本机表现为 segfault 而不是 MemoryError**，
所以报错信息具有误导性。⇒ **14B 及以上的量化加载在本机不要走 bnb**（1.5B/4B 可用）。

---

## 二、逐层流式加载：五个必踩坑（全部实测）

| # | 坑 | 现象 | 解法 |
|---|---|---|---|
| 1 | 分片**从中间切断某一层** | 分片1 = 层 0-2 完整 + 层 3 的 **9/12** 张量 ⇒ `RuntimeError: Missing key(s): self_attn.v_proj.weight, mlp.gate_proj.weight, post_attention_layernorm.weight …` | 建 **「层 → (分片, 键)」索引**（`weight_map` 直接可用），不要按分片顺序取 |
| 2 | **同时映射全部分片** | 6 × 4.5 GB = **27 GB 虚拟内存** ⇒ 第 1~2 层就 **segfault** | **只开当前层需要的分片，取完即关** |
| 3 | 每层**新建 module** | 在 L00 之后 segfault（分配开关不稳） | **复用同一个层模块**，48 次 `load_state_dict` 只换权重 |
| 4 | 独立使用子模块 | `AttentionInterface … config._attn_implementation set to None` | 显式 `cfg._attn_implementation = "sdpa"` |
| 5 | 取数不分批 | 每个 chunk 都要读一遍 27 GB ⇒ 160 chunk ≈ 80 min | **批量喂**（`--batch-chunks 16`）⇒ 一趟摊 16 个 chunk |

**成本实测**：一趟（48 层、逐层从盘搬权重）**≈ 30 s**（≈ 900 MB/s，E: 盘），摊到 16 个 512-token chunk 上。

### 保真度校验（做任何训练前必须过）
流式加载 + `lm_head` 对 prompt「用一句话解释什么是 KV 缓存：」的下一 token top-8：

| token id | logit | 文本 |
|---|---|---|
| 82707 | 16.63 | **`'KV'`** |
| 84648 | 15.42 | `' KV'` |
| 101912 | 14.20 | `'比如'` |
| 98620 | 13.33 | `' KeyValue'` |

⇒ **语义完全正确**（答案应当以 "KV 缓存是…" 开头）。这条同时盖章了 **GGUF→bf16 转换（`tools/gguf_to_hf.py`）的正确性**。

## 三、N8-S1 设计：训头**根本不需要主干常驻**

两个观察让 12 GB 单机可行：

1. **训头只要三个大张量**：`embed_tokens` + `lm_head` + `model.norm.weight` ≈ **2.9 GB**（从 `model.safetensors.index.json` 单独取）。
2. **评估 α₁ 不需要生成**：
   - 主干在位置 t 的贪心 token = `argmax(lm_head · RMSNorm(h_t))`
   - draft 的猜测 = `head(h_t, emb(x_{t+1}))` → 预测 t+2
   - 两者都能**从缓存好的 h 直接离线算**（前提：该位置 teacher-forcing 自洽，即主干贪心 == 原文下一 token）

⇒ 流程变成 **cache（流式跑一遍）→ train（只训头）→ eval（离线数接受率）**，全程显存 < 6 GB。

**数据**：`E:/models/r1-14b-mtp/hidden/c*.npz`（`h` fp16 [513, 5120] + `x` int32 [513]），语料 = 本项目 `*.md`/`*.py`（160 chunk × 512 token ≈ 82 K token）。

## 四、结果（N8-S1 完整账）

| 阶段 | 指标 | 实测 |
|---|---|---|
| cache | chunk / 用时 / 体积 | **160 chunk × 512 token / 385 s / 616 MB** |
| train v1 | lr 3e-4 恒定 600 步 | loss 52.2 → 2.96（**剧烈震荡 7.7↔2.8**） |
| train v2 | **lr 1e-4 + warmup + 余弦 2000 步** | loss 11.4 → **0.033** |
| **eval v1** | **α₁（留出集 n=5024）** | **0.3396** |
| **eval v2** | **α₁（留出集 n=5024）** | **⭐ 0.4445** |
| 基线A | 复读主干上一步 | 0.0111 |
| 基线B | 复读当前 token | 0.0111 |
| 参照 | 主干 teacher-forcing 自洽率 | 0.492 |

### 读法
1. **只改学习率调度就换来 +0.105 绝对（+31% 相对）** ⇒ v1 的震荡纯粹是 lr 太高（3e-4 恒定），
   **不是原理问题**。这条和 N2e「实现未过关 ≠ 原理证伪」是同一类教训。
2. **头比平凡基线高 40×**（0.4445 vs 0.0111）⇒ 信号真实，不是抄、不是噪声。
3. **未达 0.6 判据** ⇒ **仍不能算过关**。最可疑的原因是**过拟合**：
   训练 loss 掉到 **0.033**（几乎背下 140 个 chunk），而训练数据只有 **82 K token**，
   头却有 **327.7 M 参数**（参数量 ≈ 数据量的 4000 倍）。
4. ⚠️ **口径提醒**：α₁ 只在"主干 teacher-forcing 自洽"的 49.2% 位置上统计；
   真实投机解码的接受率还受主干自身贪心偏差影响，落地时需在 llama.cpp 侧复测。

### 下一刀的排序（按性价比）
| 优先 | 动作 | 理由 |
|---|---|---|
| ★1 | **扩 cache 到 640 chunk**（≈25 min 流式前向） | 主因是数据量 ≪ 参数量；最直接 |
| 2 | **缩小头**（去掉注意力块，改纯 MLP，≈50 M） | 降容量治过拟合，顺带省显存 |
| 3 | 延长训练 / 调 warmup 比例 | 边际收益递减，放最后 |
