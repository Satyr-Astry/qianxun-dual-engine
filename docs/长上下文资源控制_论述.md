# 长上下文的资源占用怎么压住——四层预算 + 三档降级
> 讨论时间：2026-09-24　｜　观点来源：Satyr_Astry（主张）＋ 实证检索（arXiv / 本机实测）　｜　存放：`F:\DESKTOP\AI架构与推理设计\千寻双引擎推理栈\`
> 定位：本文是「千寻」计划书 **B 轴（架构省显存）** 的深化论述，回答「怎么保证长上下文的资源占用较小」。

---

## 一、先定性：长上下文的钱花在三个不同的科目上

很多人把「长上下文贵」当成一个数字问题（上下文越长越占显存）。实际是**三个科目**，而且它们的解法完全不同：

| 科目 | 增长方式 | 什么时候成为瓶颈 | 解法归属 |
|---|---|---|---|
| **权重**（模型本身） | 与上下文**无关**（常数） | 一直是 12GB 机的硬墙（14B Q4 = 9GB） | 换小模型 / 更低比特，与本文无关 |
| **KV 缓存**（占**内存**） | **随长度线性** | 超过权重后才显眼：14B@32K f16 = 5.00 GiB，@128K = 20.00 GiB | 量化 / 低秩 / 稀疏 / 驱逐 / 架构 |
| **注意力计算与访存**（占**时间**） | decode 每步 **O(L)** 读 KV；prefill 是 **O(L²)** | **长上下文真正的杀手**：Llama-7B@32K 时 KV=16GB，读一遍 ≥11ms，占推理延迟 **>50%**（Quest 论文） | 稀疏选择 / 分页 / 内核优化 |

**关键区分：「装得下」与「每步不变慢」是两个指标，而且在长上下文下常常互相打架**（见第五节硬雷 1）。只盯显存占用会做出错误决策。

## 二、四层预算：把问题拆成四个可以独立拧的旋钮

```
L1 架构层（改一次永久有效，但要训练）      ← 收益最根本
   GQA → MLA 低秩 KV ／ 混合线性注意力（3:1 Gated DeltaNet）
L2 表示层（不动模型，只改存储格式）        ← 免费/近免费，先做
   KV q8_0（实测无损）／ 非对称 q4K+q8V ／ KIVI 2bit ／ MLA latent
L3 选择层（只在需要时读对应的 KV）          ← 收益最大，但需要内核
   Quest（query-aware 分页选择）／ SeerAttention-R（学习式，固定 token budget）／
   H2O・SnapKV（按注意力历史驱逐）／ StreamingLLM（注意力汇＋滑窗）
L4 系统层（本机 llama.cpp 今天就有的开关）   ← 零成本，立刻见效
   KV 量化 ／ 提示缓存（cache-ram）／ 上下文检查点 ／ 缓存复用 ／ 控制上下文长度
```

### L1 架构层：换掉「每 token 都要存 KV」这件事

- **GQA → MLA**（TransMLA，arXiv 2502.07864）：把 8 个 KV 头（8×128=1024）压成一个共享低秩 latent（512+64=576），**KV ↓1.78×**，且论文证明**同等 KV 预算下 MLA 表达力强于 GQA**；转换本身 68.75% 压缩只掉 1.65%。
- **混合线性注意力**（Qwen3-Next / Kimi Linear 的 3:1 结构：3 层 Gated DeltaNet + 1 层全注意力）：线性层的状态是 `O(1)` 常数，**与上下文长度完全无关**。按 40 层估：

| 方案（14B 级，40 层） | 32K | 128K | 增长方式 |
|---|---|---|---|
| 纯注意力 f16 | 5.00 GiB | **20.00 GiB** | 线性 |
| 混合 3:1（10 全注意力层）f16 | 1.25 GiB | **5.00 GiB** | 线性但 ÷4 |
| 混合 3:1 + 线性层状态（30×16×128×128 fp16） | +15 MiB | **+15 MiB（常数）** | **O(1)** ✅ |

**Qwen 已经把家族主线押在这条路上**（Qwen3.5/3.6/3.7/3.8 全系混合），所以「换载体」是长期解 —— 但有硬代价（第五节雷 3）。

### L2 表示层：量化（今天就能做，收益/成本比最高）

| 方案 | 压缩比 | 代价 | 证据 |
|---|---|---|---|
| **KV q8_0** | 2× | PPL 实测**无损**，32K 省 2.11 GiB | 多处 A100/Qwen3-8B 实测：q8_0 PPL 在误差内 |
| 非对称 q4 K + q8 V | 2.7× | +0.4% PPL | 实测优于对称 q4/q4 |
| q4 K + q4 V | 4× | **尾部崩**：99.9% KLD 比 q5_0 高 32%，会**破坏 tool call**；另有实测输出相似度掉到 8.3% | anbeeld 长上下文 KV 基准 |
| **KIVI 2bit**（K 按通道、V 按 token） | **8×** | 2.6× 峰值内存下降，质量近乎不变（免微调） | arXiv 2402.02750；尚未进 llama.cpp |
| MLA latent | 1.78× | 需训练（6B token 级才能完全复原） | arXiv 2502.07864 |

**结论：`-ctk q8_0 -ctv q8_0` 是「免费午餐」；再往下压必须换轴（低秩/稀疏），不要在 4bit 上赌。**

### L3 选择层：让每步只读「该读的那部分」（收益最大）

- **Quest**（ICML 2024，arXiv 2406.10774）：分页保存每页 K 的**逐通道最大/最小值**做摘要，用当前 Q 估算每页注意力上界，只加载 Top-K 页；32K 上下文 **self-attention 7.03× 加速、端到端 2.23×**，且**不丢弃** KV（保留全部，只是不读）。选择开销随序列增长趋近 `1/页大小`，Top-K 过滤在 128K 内仅 5–10 µs。
- **SeerAttention-R**（arXiv 2410.13276）：**学习式**门控预测哪些块重要，固定 `token_budget`（解码用 4096 起）→ **每步代价与上下文长度解耦**；官方已发布 Qwen3-4B/8B/14B 的 AttnGate 权重（66–84MB），**只训门控、主干冻结**。
- **DSA**（DeepSeek-V3.2，arXiv 2512.02556）：lightning indexer 打分 + 细粒度选 2048 个 KV（`index_topk=2048`），把主注意力从 `O(L²)` 降到 `O(L·k)`；indexer 自身缓存每 token 仅 1 头 × 128 维（fp8）。
- **驱逐类**（H2O arXiv 2306.14048 / SnapKV arXiv 2404.14469 / StreamingLLM arXiv 2309.17453）：直接丢弃 token，**对「相关证据分散在全上下文」的任务会崩**（Quest 实测：H2O 式历史驱逐的 Top-10 召回率显著低于全注意力）；适合摘要/QA/无限聊天。
- **提示压缩**（LLMLingua-2，arXiv 2403.12968）：在**输入侧**做 2–5× 压缩，端到端 1.6–2.9×、显存最多 ↓8×；但 2026 的系统评测提醒：在已优化的框架（vLLM）下、prompt <4K 时**压缩开销会吃掉收益**，只在 >5K token 且压缩比 >4× 时明显。

**本机约束**：Quest/MInference/SeerAttention 都需要**定制内核**（block-sparse FlashAttention），本机无 MSVC/cmake → **L3 只能走 python/vLLM 研究支线，不进主运行时**（千寻计划书 R3）。

### L4 系统层：本机 llama.cpp b10938 已有的旋钮（今天就能用）

| 开关 | 作用 | 建议值 |
|---|---|---|
| `-ctk q8_0 -ctv q8_0` | KV 减半，实测无损 | **默认开**（务必配 `-fa on`） |
| `-c N` | 只分配**实际需要**的上下文，别开满 | 按用途设 8K/16K/32K |
| `-cram, --cache-ram N` | 提示缓存上限（默认 8192 MiB，放 RAM） | 8192 |
| `--cache-reuse N` | 多轮对话复用已算过的前段 KV（避免重复 prefill） | 256 起试 |
| `-ctxcp, --ctx-checkpoints N` | 上下文检查点（默认 32），配合回滚/重放 | 保持默认 |
| `-kvo/-nkvo` | KV 是否允许卸载 | 保持默认开启（配合分层） |
| `--swa-full` | 用全尺寸 SWA 缓存（滑窗模型专用） | 滑窗/混合模型才需要 |

## 三、本机实测数字（Qwen3-14B：40 层 × 8 KV 头 × head_dim 128）

### 3.1 每 token 的 KV 成本

| 精度 | 每 token | 1K | 32K | 128K |
|---|---|---|---|---|
| f16 | **160.0 KiB** | 160 MiB | 5.00 GiB | 20.00 GiB |
| q8_0 | 80.0 KiB | 80 MiB | 2.50 GiB | 10.00 GiB |
| q4_0 | 40.0 KiB | 40 MiB | 1.25 GiB | 5.00 GiB |
| KIVI 2bit | 20.0 KiB | 20 MiB | 0.62 GiB | 2.50 GiB |
| MLA latent(512+64, f16) | 45.0 KiB | 45 MiB | 1.41 GiB | 5.62 GiB |
| DSA indexer(1头 fp8) | 5.0 KiB | 5 MiB | 0.16 GiB | 0.62 GiB |

> 8B（36 层）：f16 = 144 KiB/token → 32K 4.50 GiB / 128K 18.00 GiB；q8 减半。

### 3.2 **解码每步的 KV 读取量**（决定速度，比总占用更重要）

| 策略（128K 上下文） | 每步读取 | 4070 Ti（504 GB/s）耗时 |
|---|---|---|
| 全量 f16 | 20480 MiB | **39.68 ms/步** |
| 全量 q8 | 10240 MiB | 19.84 ms/步 |
| 稀疏 read top-4096 (f16) | 640 MiB | **1.24 ms/步** |
| 稀疏 read top-4096 (q8) | 320 MiB | **0.62 ms/步** |
| 稀疏 read top-2048 (q8, DSA 式) | 160 MiB | 0.31 ms/步 |

**这就是「长上下文不涨成本」的数学本质：把每步读取量从 `O(L)` 变成 `O(k)`（k 固定）**。128K 时全量 f16 光 KV 就要 39.7ms/步（≈25 tok/s 上限），稀疏后降到 1.2ms/步。

### 3.3 12GB 上「到底哪套组合放得下」（权重 + KV + MTP 头 0.5 + 开销 0.3）

| 配置 | 合计 | 判定 |
|---|---|---|
| 14B + 8K + q8 KV | 10.43 GiB | ✅ |
| 14B + 16K + q8 KV | 11.05 GiB | ✅（临界） |
| 14B + 32K + q8 KV | 12.30 GiB | ❌ 溢出 |
| **14B + 32K + q8 KV + MLA** | **10.50 GiB** | ✅ |
| 14B + 128K + q8 KV + MLA | 12.61 GiB | ❌ 溢出 |
| 8B + 32K + q8 KV | 8.30 GiB | ✅（宽松） |
| 8B + 128K + q4 KV | 10.80 GiB | ✅（质量有尾部风险） |

### 3.4 分层存储（KV 放 CPU/RAM）在本机可不可行

| 做法 | 每步耗时 | 判定 |
|---|---|---|
| 每步从 RAM/PCIe 搬 1 GiB | PCIe 31 ms ／ DDR4 25 ms | ❌ |
| 每步搬 2 GiB | 62 ms ／ 50 ms | ❌ |
| 每步搬 5 GiB | 156 ms ／ 125 ms | ❌ |
| **只搬「被选中的 4096 token」(q8, 320 MiB)** | PCIe **9.8 ms** | ⚠️ 勉强可行，需 InfiniGen 式按需预取 |

**所以「KV 放系统内存」在单机单流下只有一种活法：先用摘要/索引判断该读什么，再只搬那部分**（InfiniGen，OSDI'24，arXiv 2406.19707：用上一层信息预测下一层需要的 KV，只预取必要条目，比既有卸载方案快 **3.0×**）。无脑分层 = 每步几百毫秒 = 不可用。

## 四、三档降级策略（工程上怎么执行）

```
先看用途，再定「长度预算」：
  ① 日常对话/单轮问答     → 目标 8–16K，q8 KV，全显存，速度优先
  ② 长文档审阅/代码库     → 目标 32K，q8 KV + 缓存复用；装不下就上 MLA 或换 8B
  ③ 超长（>32K）/ 多轮长历史 → 不要硬塞：改走「检索 + 分段 + 摘要」，
                             或只在 python/vLLM 侧开稀疏内核
```

- **档 0（免费，立刻做）**：`-ctk q8_0 -ctv q8_0 -fa on` + 按用途设 `-c` + `--cache-ram 8192` + `--cache-reuse`。14B 32K：5.00 → 2.50 GiB。
- **档 1（省显存但不掉速，需内核）**：稀疏选择（Quest/SeerAttention-R/DSA 式）。**每步读取量常数化**，同时省显存与省时间。本机不可编译 → 走研究支线（M3）。
- **档 2（质量换资源）**：驱逐（H2O/SnapKV/StreamingLLM）+ 提示压缩（LLMLingua-2）。**只砍能砍的**：摘要/QA/聊天可砍；「证据分散」的检索、代码跨文件引用**不要砍**。
- **档 3（架构换根子）**：MLA（1.78×，可恢复）或混合线性（O(1) 状态，但需换模型族）。

## 五、硬雷与反直觉（本节是本文最值钱的部分）

| # | 反直觉结论 | 实证 |
|---|---|---|
| 1 | **量化 KV 会拖慢「深上下文」的解码**，省显存 ≠ 更快 | 实测 Qwen3-8B：q8_0 解码在 8K 深度是 f16 的 **80%**，到 **64K 深度只剩 55%**（q4_0 50%）——每步都要反量化，代价随深度增长。所以长上下文场景要在「装得下」和「不变慢」之间做显式取舍 |
| 2 | **KV 量化在浅上下文基本免费，在深上下文才开始收税** | 同一实测：8K 缓存下量化 KV 只贵 20% |
| 3 | **省显存架构与投机解码互斥** | 混合循环（gated DeltaNet）模型投机需回滚循环状态：Qwen3.5-27B 实测 α=47.5% 仍**净亏**（2-token 验证批要 1.75× 时间）；llama.cpp PR #22400 修了才在别的模型上拿到 1.78×。**12GB 机上「长上下文省显存」和「投机提速」可能只能二选一** |
| 4 | **驱逐类方法在「证据分散」任务上会静默崩** | H2O 式按历史驱逐的 Top-10 注意力召回率明显低于全注意力（Quest 论文）；StreamingLLM 只对近期信息有效 |
| 5 | **PPL 看不出 KV 压缩的伤害，尾部 KLD 才看得出** | q4_0 的 PPL 只涨 0.01，但 99.9% 分位 KLD 比 q5_0 高 32% —— 会**破坏 tool call / 结构化输出**。验收必须看尾部，不看均值 |
| 6 | **提示压缩在已优化的框架里可能白干** | 2026 评测：vLLM 下 prompt <4K、压缩比 ≤5 时压缩开销吃掉收益；只在 >5K 且压缩比 >4 才有净赚 |
| 7 | **12GB 上「14B + 128K」不存在可行解** | 即使 q8 KV 也要 10 GiB + 权重 9GB；必须 MLA（且仍临界）或换 8B（q4 KV 才有尾部风险） |
| 8 | **上下文复用是最便宜的大招，却最常被忽略** | 多轮对话/重复文档场景，命中缓存后 prefill 成本≈0；32K 全量重算要扫 5 GiB KV |

## 六、给「千寻」的落地配置（本机可即用）

```bash
# ① 默认（速度优先，≤16K）
llama-server -m <model.gguf> -ngl 99 -c 16384 -fa on \
  -ctk q8_0 -ctv q8_0 --cache-ram 8192 --cache-reuse 256

# ② 长文档（32K，8B 更稳）
llama-server -m <qwen3-8b.gguf> -ngl 99 -c 32768 -fa on \
  -ctk q8_0 -ctv q8_0 --cache-ram 8192

# ③ 14B + 32K：先看显存（会临界），不行就降 8B 或上 MLA 支线（M5）
nvidia-smi --query-gpu=memory.used,memory.total --format=csv
```

**明确不做**：不在本机编译 block-sparse 内核；不用 q4/q4 KV；不为「14B+128K」硬撑（部分卸载后只剩 3–6 tok/s，比 8B 全显存差 20 倍）；不把 KV 无脑卸载到 RAM（每步 25–125 ms）。

**验收方法（比 PPL 严格）**：
1. 峰值显存（1Hz nvidia-smi）
2. **每步 KV 读取量 / decode tok/s 随上下文深度**（8K/16K/32K/64K 四档，这是最能暴露问题的一条曲线）
3. 尾部风险：99.9% 分位 KLD ／ tool-call 成功率 ／ 结构化输出合法率
4. 长依赖任务：passkey retrieval + LongBench 子集（**不能只看 PPL**）

## 七、一句话收束

压住长上下文不是找一个技巧，而是**按顺序拧四个旋钮**：量化（免费）→ 缓存复用与长度预算（免费）→ 稀疏选择（收益最大，但需内核）→ 架构替换（最根本，但需训练、且与投机解码互斥）。并且全程要同时盯两个指标——**「装得下」和「每步不变慢」**；在长上下文里，这两个指标经常互相拖后腿，谁优先由用途决定。
