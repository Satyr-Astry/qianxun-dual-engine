3. **D（ngram 投机）没有拿到接受率**（`draft_n=null`，decode 43.4 ≈ B 的 44.0 ⇒ 基本没生效）。
   待查项：本 build 的 ngram 档可能需要额外开关（或 `/completion` 不报 draft 字段）→ 第二轮之后单独验证。

## 第二轮（**真喂长上下文**，进行中）——已拿到的硬数据

### C_q8_d16k：16K token 真上下文 —— **结果已出（关键负面对照）**
prefill 曲线（实时取自 server 日志）：

| 已处理 token | 2 048 | 4 096 | 6 144 | 8 192 | 10 240 | 12 288 | 14 336 | **完成 14 945** |
|---|---|---|---|---|---|---|---|---|
| prefill tok/s | 226.8 | 155.5 | 125.2 | 105.3 | 91.1 | 80.3 | 71.2 | **64.9（累计均值）** |

**prefill 从 2K 到 15K 衰减 3.5×（226.8 → 64.9 tok/s）**

**decode 结果（最刺眼的一条）**：
| 上下文 | decode tok/s | 每 token 耗时 |
|---|---|---|
| d0（B，q8 KV） | **44.0** | 22.7 ms |
| **d16K（C，q8 KV）** | **4.73** | **211.3 ms** |

⇒ **16K 上下文把解码拖慢了 9.3×**。而按 KV 读取量估算（16K × 96 KiB = 1.5 GiB ÷ 504 GB/s ≈ 3 ms/token），
**211 ms 远超带宽预期** ⇒ 强烈怀疑 **KV/计算缓冲已溢出到主机内存**（GPU 占用 11826/12282 MiB 贴顶；
此前会话也记录过"部分卸载只剩 3.6 tok/s"，量级吻合）。
⚠️ **这条必须先定性**（是"KV 溢出主机内存"还是"q8 KV 的慢路径"）——它决定三轴方案该打哪个靶子：见待补项。

### 🎯 4.73 tok/s 的根因：**显存超额 + VMM 页交换（已拿到分配明细）**

H 组（`-v`）的加载明细：
```
CUDA0 model buffer size   = 8148.38 MiB     ← 权重（Q4_K_M）
CUDA0 KV buffer size      = 4080.00 MiB     ← q8 KV @ ctx 40960
CUDA0 compute buffer size =  240.09 MiB
CUDA_Host compute buffer  =   60.09 MiB
合计 12,468.6 MiB  >  物理 12,282 MiB   ⇒ 超额 ≈ 187 MiB
```
另：`llama_init_from_model: enabling flash_attn since it is required for quantized V cache`（q8 V 强制 FA）。

**⇒ 结论：卡片装不下时 llama.cpp 不报错、也不自动降级层数，而是「静默超额」；
本机 `VMM: yes` ⇒ 驱动把超出的部分放到系统内存，每步解码都要过 PCIe。**
这解释了：d0 44 tok/s → d4K 9.33 → d16K 4.73（G/H 实测），且实测值与 PCIe 带宽量级吻合：
- 4K：KV q8 = 384 MiB ÷ ~6 GB/s ≈ 64 ms（实测 107 ms）
- 16K：KV q8 = 1.5 GiB ÷ ~6 GB/s ≈ 256 ms（实测 211 ms）

**这条把三轴方案的靶子彻底改写**：本机上下文轴的瓶颈**不是"KV 太大"**，而是
**"KV+权重+计算缓冲一旦超过物理显存，性能会从 ~44 tok/s 直接掉到 ~5–9 tok/s（9×），而且是静默发生"**。
⇒ 正确做法是**留出安全余量**（KV 预算 = 12282 − 8148 − 240 − 60 ≈ **3834 MiB**，
q8 下 ≈ **40.9K token 理论上限，但必须留余量**），而不是"能塞多少塞多少"。

**因果验证（进行中，J 组）**：同样 16K 真上下文，只把 `-c` 从 40960 收到 32768
（KV 4080 → 3072 MiB，合计 11460 MiB **不超额**）⇒ 若 decode 回升到 ~40 tok/s，则"超额=根因"成立。

### E_f16_d32k：**确认装不下**（负结果，留证）
server 日志：`common_fit_params: failed to fit params to free device memory: n_gpu_layers already set by user to 99, abort`
⇒ f16 KV 在 32K 上（32K × 192 KiB = 6.0 GiB + 8.37 GiB 权重）**放不进 12 GB 卡**，
这正是"上下文容量"轴的核心证据：**同模型同长度，只换 KV 精度，一个装不下、一个能跑。**

### 「每步不变慢」的待测项
C（16K）与 F（32K）的**decode tok/s** 出来后，与 B（d0）对比即可给出判据结论（目标：降幅 ≤30%）。

## 第六轮：⚠️ **prefill 悖论**（Q2 vs Q1：同 16K 内容，prefill 差 21×）

| 组 | 权重卸载 | 加载期合计（探针） | **prefill tok/s** | prefill 耗时 | decode tok/s |
|---|---|---|---|---|---|
| Q1 | 无 | 11665 MiB（余 617） | **73.1** | 204.4 s | 25.5 |
| **Q2** | 末 8 层 FFN 下 CPU | 10704 MiB（余 1631） | **1538.1** | **9.7 s** | 19.5 |
| Q4 | 末 8 层 FFN 下 CPU | —— | 48.8（30K 平均） | 626.7 s | 15.4 |

**同一 16K token 内容，prefill 从 204 秒掉到 9.7 秒 —— 21×，而两者加载期的显存只差 961 MiB。**

**机理解释（Q5 已证伪"小批量"假设，但与"余量"规律完全吻合）**：
`--probe` 量的是**加载稳态**（空批量下 compute buffer 仅 200–272 MiB），而**prefill 峰值**出现在处理
整段提示时（激活 + FA 工作区 + CUDA graph）。**余量不够 ⇒ ggml 把图静默拆到 CPU ⇒ prefill 塌 20–30×。**

### ★ 已成型规则：**prefill 速度由"加载期余量"决定**（4 个数据点）
| 组 | 配置 | **加载期余量** | prefill tok/s | decode tok/s |
|---|---|---|---|---|
| Q1 | q8, ctx 32768, 不卸载 | 617 MiB | 73.1 | 25.5 |
| **Q5** | 同 Q1 **+ 小批量 `-b 512 -ub 256`** | 617 MiB | **72.6（无效）** | **26.9** |
| **Q2** | q8, ctx 32768, **末 8 层 FFN 下 CPU** | **1578 MiB** | **1538.1** ⭐ | 19.5 |
| Q4 | q8, ctx 40960, 末 8 层 FFN 下 CPU | 762 MiB | 48.8 | 15.4 |

**规则**：**加载期余量 ≥ ~1.5 GiB ⇒ prefill ≈1500 tok/s；余量 < ~0.8 GiB ⇒ prefill 塌到 50–75 tok/s（20–30×）。
压小批量（`-b/-ub`）**无效** —— 买余量只能靠"少放权重"（`-ot`）或"少要 KV"（收 ctx / 压 V）。**

**⇒ 三条本机规范（新增）**
1. **`--probe` 只保证"能加载"，不保证"prefill 不溢出"** ⇒ 另需 **≥1.5 GiB 的 prefill 峰值余量**。
2. **prefill 与 decode 的最优配置不同，且互相拉扯**：
   - TTFT 优先（读长文档）⇒ 大余量（`-ot`）：16K 只花 **9.7 s**；代价 decode 25.5→19.5
   - decode 优先（长对话）⇒ 不卸载：25.5–26.9 tok/s；代价 16K prefill **204 s**
3. **小批量不是解药**（实测无效），别在 `-b/-ub` 上浪费时间。

**Q6（已完成，全场最优）**：不卸载、ctx **24576**（余量 ~1434 MiB）
⇒ **prefill 2202.1 tok/s、decode 37.8 tok/s**（16K 真上下文，全程 13.5 s）

## ★★ 第七轮：**本机性能总规律（已闭环）**—— 一条数字预测 20–30× 悬崖

| 组 | 配置 | **加载期余量** | prefill tok/s | decode tok/s |
|---|---|---|---|---|
| Q1 | q8, ctx 32768, 不卸载 | 617 MiB | 73.1 | 25.5 |
| Q5 | 同 Q1 + `-b 512 -ub 256` | 617 MiB | **72.6（小批量无效）** | 26.9 |
| **Q6** | **q8, ctx 24576, 不卸载** | **1434 MiB** | **2202.1** | **37.8** |
| Q2 | q8, ctx 32768, 末 8 层 FFN 下 CPU | 1578 MiB | 1538.1 | 19.5 |
| Q4 | q8, ctx 40960, 末 8 层 FFN 下 CPU | 762 MiB | 48.8 | 15.4 |
| B | q8, ctx 8192 | ~3.8 GiB | 1038 | 44.0 |

### 规律（本机第一条可预测的性能定律）
**加载期余量（`--probe` 给出的 `12282 − total`）决定一切：**
- **余量 ≥ ~1.4 GiB** ⇒ prefill **1500–2200 tok/s**、decode **37.8–44**（健康区）
- **余量 0.6–0.8 GiB** ⇒ prefill 塌到 **49–73 tok/s（20–30×）**、decode 也降（15–25）（悬崖区）
- **余量为负（超额）** ⇒ 直接崩到 **4.7 tok/s**（灾难区）

**⇒ 本机铁律（最终版）**：
1. **配置前先跑 `--probe`，把 `total` 压到 ≤ 10850 MiB（即余量 ≥ 1.4 GiB）** —— 这一条同时买到快 prefill 与快 decode。
2. **`--probe` 只保证"能加载"，不保证"prefill 不溢出"** —— 加载期余量才是 prefill 的判据。
3. **压小批量（`-b/-ub`）无效**，别再试。
4. **要换余量只有两种货币**：少放权重（`-ot` 把层下 CPU）或 少要 KV（收 `-c` / 压 V）。

### 配置菜单（全部实测）
| 用途 | 配置 | 余量 | prefill | decode |
|---|---|---|---|---|
| **推荐日常（≤16K 上下文）** | `-c 24576 -ctk q8_0 -ctv q8_0`（不卸载） | 1434 | **2202** | **37.8** |
| 32K 长文、要低 TTFT | `-c 32768 -ctk q8_0 -ctv q8_0 -ot "blk\.(4[0-7])\.ffn.*=CPU"` | 1578 | 1538 | 19.5 |
| 16K 会话、decode 优先 | `-c 32768 -ctk q8_0 -ctv q8_0` | 617 | 73 | 25.5 |
| 32K 极限（不推荐） | `-c 40960 -ctk q8_0 -ctv q8_0 -ot …` | 762 | 48.8 | 15.4 |
| ⛔ 绝不要 | `-c 40960`（不卸载）= 超额 247 MiB | −247 | —— | 4.7 |

**⇒ 对架构的意义**：这 20–30× 的悬崖**不是算法问题、也不是算力问题，而是"显存预算分配"问题**。
我们原以为"长上下文变慢"要靠稀疏注意力/记忆页去治；实测表明**先得把预算分配治对**（第一条就白拿 5.4×），
**剩下那截（37.8→44 的差 + 32K 时的降幅）才是记忆页与写入门控真正的战场。**

## 第八轮：K4 投机解码（免训练档）——**+15%，已生效**

4. 本 build 的 `/completion timings` **不返回 draft 计数**（S1/S3 的 `draft_n` 均为 null）⇒
