# 静默态底层 × 千寻：分层记忆与预取接口设计
> 作者：Satyr_Astry　｜　2026-09-24　｜　存：`F:\DESKTOP\AI架构与推理设计\千寻双引擎推理栈\`
> 输入：《静默态底层：渐进式 KV 层级与主动激活网》（三层记忆体 + 双通道激活 + 可学习路由 + 与静默态接合）
> 本文回答：**这套底层设计在本机（12GB VRAM + 16GB DRAM，无编译链）上的可执行形态是什么**，哪些今天就能落地、哪些只能进研究支线，以及它给「千寻」带来的三个新增量。
>
> **结论先行**：三层记忆体在本机成立；但**「远端召回 + 静默态预取」只有一种可行形式——预取「索引/摘要」与「已算好的前缀（提示缓存）」，绝不是每步回拉 KV 本体**（数字见 §3）。判据一句话：**凡是每步都要搬的，否决；一次搬好之后复用的，采纳。**

## 1. 逐条复核原文的实证依据（先查再谈工程）

| # | 原文主张 | 复核结果 | 裁决 |
|---|---|---|---|
| 1 | 全 KV 驻显存不合理，生产早已热/温/冷分层 | ✅ **Strata**（OSDI'26，arXiv 2508.18572，已并入 SGLang 生产）：40GB HBM 只够 8B 存约 **0.3M token**；且**分层本身引入新瓶颈**——即使优化 I/O 后仍有 **24% prefill 时间卡在装载**，系统是 *loading-bound* 而非 compute-bound | ✅ 成立，且比原文更严重 |
| 2 | 稀疏注意力「近端过激活、远端饿死」是第一性缺陷 | ✅ **arXiv 2607.13205** 给出更硬的机制：schema-dense 上下文（嵌套 JSON/表格）里 **DELIM 每 token 注意力质量 13.64 vs VALUE 0.336 ≈ 40×**；H2O 把结构噪声当信号 → **leaf-value QA 的 EM 从 88% 崩到 0%**（5% 预算）；KEY 被过度保留 **1.8–1.9×**；**第 0 层会反转**（VALUE>KEY） | ✅ 成立，且原文「用正交性判据替代」的方向被间接支持 |

| 4 | 分层要「索引常驻、找数据不回拉数据」 | ✅ **KVSwap**（arXiv 2511.11907，端侧磁盘感知卸载）正是这个形态：**全量缓存放盘 + 极紧凑内存元数据预测该预载哪些条目 + 计算与磁盘访问重叠** | ✅ 且**它是端侧路线**，与本源最贴 |
| 5 | OrthoRank（arXiv 2507.03865）「越正交于 sink 越重要」 | ⚠️ 本次未取到权威页（检索通道失败） | **待复核**：用之前必须先查到原文，否则不写进实现 |

## 2. 从「三层记忆体」到本机的四层预算（映射与容量）

| 原文层 | 本机物质 | **实测容量** | 访问代价 | 裁决 |
|---|---|---|---|---|
| **L0 VRAM 激活集** | 12GB − 权重 − MTP 头 − 开销 | 14B：剩 2.40 GiB → **15.7K token (f16) / 31.5K (q8)**；8B：剩 6.40 GiB → **46.6K / 93.2K** | HBM ≈504 GB/s | ✅ 主战场 |
| **L1 DRAM 温数据** | 16GB 里空闲 ≈9.7GB | 14B：**63.6K token (f16) / 127K (q8)**；8B：**70.6K / 141K** | PCIe 4.0x16 32GB/s：一页(64 token)=**0.15–0.31 ms**；4096 token=**9–20 ms** | ⚠️ 只在**按页按需回拉**时可行 |
| **L2 NVMe 冷数据** | 磁盘（KB 级 I/O） | 近乎无限 | 更低一档 | ⚠️ 只放**索引与素材** |
| **索引常驻** | 角色探针 / 检索索引 | 2607.13205 的**线性角色探针仅 15MB** | 可常驻 | ✅ **本机最值得做的一层** |

## 3. 三个决定性数字（用来裁决「预取」到底可不可行）

| 动作 | 代价 | 裁决 |
|---|---|---|
| 每步回拉 1 GiB KV（PCIe） | **31 ms/步**；走 DDR4 约 25 ms/步 | ❌ 不可行 |
| 每步只回拉「被选中的 4096 token」(q8) | **9.8 ms/步**（14B q8） | ⚠️ 边界可行，但需要页级选择内核 |
| **一次性预热：32K 文档的 KV = 2.25–5.00 GiB** | prefill 要算 32768 token（数十秒级）；**命中提示缓存 ≈ 0** | ✅ **这才是「用静默态时间换响应态零等待」在本机的真实形态** |

**并且容量上还有一个硬约束**：14B 场景 L0 只剩 2.40 GiB，而 32K 的 q8 KV 要 2.50 GiB → **放不进显存** ⇒ 14B 的预热只能落在 **DRAM 提示缓存**；8B 场景剩 6.40 GiB ≥ 2.25 GiB ⇒ **可以同机显存预热**。
→ **静默态预热应当先在 8B 上做**（与 T11 的结论一致：8B 才是本机的高体验组合）。

## 4. 本机可执行形态：「静默态预热 worker」（今天就能落地，无需内核）

llama.cpp b10938 **已经有实现这套语义的原生开关**（已实测 `--help`）：

| 开关 | 对应原文概念 |
|---|---|
| `-cram, --cache-ram N`（默认 8192 MiB） | L1 DRAM 作为提示缓存层 |
| `--cache-idle-slots`（默认开，需 cache-ram） | **「静默态写入」的原生实现**：空闲槽在接到新任务时把 KV 存入提示缓存 |
| `--cache-reuse N` | 前段 KV 复用，避免重复 prefill |
| `-ctxcp, --ctx-checkpoints N`（默认 32） | 上下文检查点（页表语义的雏形） |
| `-ctk/-ctv q8_0` | 同样容量多装一倍 token |

**设计（M7.0）**：
```
空闲窗口判定（无请求 ∧ 显存余量 > X ∧ 未在跑 ComfyUI/训练）
        ↓
后台对「可能被问到」的文档/代码库发一次 prefill-only 预热请求
        ↓
KV 落入提示缓存（DRAM）；索引/摘要落盘常驻
        ↓
用户真提问 → 命中前缀 → TTFT 从数十秒 → 接近 0；decode 速度不变
```
**验收**：同一份 32K 文档，冷启动 TTFT vs 预热后 TTFT（记录 `prompt_ms`）；decode tok/s 不得因预热变慢。

## 5. 与 T11 结论的「看似冲突」与和解

T11 明确否决了「KV 卸载到 RAM（每步 25–125 ms）」，而本篇却采纳「静默态预取」。二者其实**是两个不同对象**：

| 维度 | 卸载 + 每步回拉（**否**） | 预热提示缓存（**采**） |
|---|---|---|
| 发生时机 | 每个 decode 步 | 请求到达**之前**（离线完成） |
| 传输量 | 每步全量或选中页 | **一次性写入，之后零传输** |
| 对延迟影响 | **+9.8 ~ 125 ms/步** | **TTFT 降一个数量级**，decode 不变 |
| 依赖 | 需要页级选择内核（本机不具备） | llama.cpp 现成开关 |

**→ 项目铁律（新增）**：**凡「每步都要搬」的，一律否决；凡「一次搬好、之后复用」的，优先采纳。**

## 6. 与千寻四轴的接口

| 轴 | 接口 |
|---|---|
| **B 轴（T11 长上下文）** | 「索引常驻 + 分页预取」是 L3 选择层在本机**唯一无需内核的子集**；L0/L1/L2 容量表已并入本文 §2 |
| **D 轴（T12 自进化）** | 静默态的产物是**索引更新 / 知识沉淀 / 提示缓存预热**三类，**全部不改权重** → 静默态天然属于 B/C 类，必须与自进化的 **A 类（动权重）** 显式分离，严禁混线 |
| **C5 联合调度** | 静默态窗口要作为一等调度资源（显存余量、无请求、功耗/温度），并受「双轴重校准」约束（换 adapter 后索引与热度统计一并失效） |
| **能量约束** | 静默态常驻 = 烧卡 + 抢 ComfyUI。必须定义**窗口与预算**（例如：用户离开 >5 min 且 GPU 空闲才启动，单轮 < N 分钟，跑完即释放） |

## 7. 三个新增量（本文对原设计文档的回礼）

1. **把「预取」重定义为「预热已算好的前缀」**——这是静默态-存储层级接口在本机唯一成立的形态；并把判据固化为「每步搬 = 不搬」。
2. **索引常驻优先于 KV 常驻**：2607.13205 的**角色探针只有 15MB**、KVSwap 用**极紧凑元数据**预测预载——本机的「索引」应是**结构角色 + 语义摘要 + 热度统计**，而不是 KV 本体。这也解释了为什么 L2 该放素材与索引，而不是放一堆等回拉的 KV。
3. **静默态产物三分类**（索引 / 知识 / 预热）→ 与自进化 A 类解耦，避免出现「静默态训练」这种高风险混线。

## 8. 硬雷与不做清单（本机）

| # | 不做 | 依据 |
|---|---|---|
| 1 | ❌ 不做 KV 本体的每步回拉 | 9.8–125 ms/步（§3/§5） |
| 2 | ❌ 不用「按注意力质量」选 token 的驱逐 | 2607.13205：结构噪声赢，EM 88%→0%；且第 0 层反转 |
| 3 | ⚠️ 正交性判据（OrthoRank）**待复核**后再用 | §1 #5 |
| 4 | ⚠️ 远端召回 / MoBA / NSA / DSA 需要 block-sparse 内核 | 本机无 MSVC/cmake → 只进 python/vLLM 研究支线（与 T11 的 L3 同归 M3） |
| 5 | ⚠️ 静默态常驻必须设窗口与预算 | 否则烧卡、抢 ComfyUI（既有结论：静默态常驻 = 烧卡） |
| 6 | ⚠️ 若为「常数状态」换混合线性载体，要付投机解码互斥的代价 | T11 硬雷 2（Qwen3.5-27B α=47.5% 仍净亏） |

## 11. 一句话收束

原文把「静默态」与「存储层级」焊在一起是对的，但**在这台机器上，焊缝只有一个位置能承重**：**索引常驻、KV 不常驻；一次搬好、之后零搬。** 凡是要求「每一步都把数据搬回来」的设计，无论多优雅，在本机都过不了 10 ms/步 这道线。
